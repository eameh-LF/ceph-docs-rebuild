Ceph documentation · Proposal to the team · September 2026

Ceph Docs Rebuild

Status For team review and approval

Since April I have been on cleanup: 65 defects found, 32 fixed or in review, the rest still in hand. Necessary work, but it fixes pages one at a time and never gets ahead of the problem. The structure itself has to change: stop treating the docs as pages to fix, and rebuild them around what the reader is trying to do. Three moves.

01

Three moves

1

A new architecture: seven doors, one shape

The top level becomes seven doors, ordered by what the reader is doing. Inside every storage service the same five parts appear in the same order, so once you have learned one section you can find your way around the rest. Nothing is deleted: all 618 pages already have a home, listed page by page in the companion map, and pages only move once the new navigation works.

Parts of the tree already do this. CephFS groups its pages this way but hides the headings, and RADOS is already split by task. This finishes the job and makes it visible everywhere.

Page counts are today's pages mapped to each door. About 90 need rewriting; the other 528 need a new home and some metadata. Kubernetes and Django are organised this way, and Canonical and Cloudflare have adopted the same model.

2

Modular pages: three types, one template

Every page becomes one of three types and follows one template. A procedure covers one task, says which releases it applies to, and ends with how to check it worked. Repeated procedures are written once and pulled in wherever they are needed, so they cannot drift apart. Creating a pool for RBD images is written out six times in the Block section today, and only one of those copies tells you how to verify it.

Command reference stays in the man pages, so it still works offline. Prose pages pull the entry from there when the docs are built, rather than repeating it. The first trial is already up as PR 71609.

Concept

Explains one idea the reader needs before acting. No commands, no steps.

Procedure

One task, numbered steps, one command per step, expected output, verification.

Reference

Facts to look up, not remember: options, commands, limits. Generated from source where possible.

Create an erasure-coded pool
type: procedure · applies to: Squid, Tentacle · reviewed: 2026-09 · owner: rados
Before you startCluster health, permissions, an EC profile chosen
StepsNumbered. One command each, with the output you should see
VerifyThe command that proves it worked
If it failsThe two or three most common failures and what they mean
RelatedThe concept behind it, the reference for every option
House rulesCross-link related pages generously. Example values fail safely if pasted (osd.1701, not osd.0)

Red Hat and IBM already write their Ceph guides this way, with the same prerequisites, procedure and verification shape.

3

Machine-readable, as a byproduct

This is not a workstream and needs no budget. It falls out of moves 1 and 2: one build change, plus the metadata the template already adds. More people now ask an AI assistant about Ceph, and those assistants read docs.ceph.com. Today they get HTML with no index, and nothing on the page says which release it applies to. The source stays reStructuredText; these outputs are generated by the build, exactly as the HTML is.

What AI assistants needTodayAfter the rebuild
An index of the docsMissingthe standard index file, llms.txt, is not thereGenerated by the build and served at the site root
A plain-text copy of each pageHiddenone exists, but nothing links to itA Markdown copy of every page, linked and listed in the index
Which release a page applies toNothingno page carries that, or a review date, or an ownerRelease, review date and owner on every page
Options and commands as dataUnpublishedthe build already reads them, but only to make HTMLPublished as data beside the pages

Two smaller things follow: stable anchors, so a page or a single procedure can be cited, and as a stretch a service that lets an assistant query the docs directly. llms.txt is already served by Anthropic, Cloudflare, GitHub, AWS and 87 of the top 1,000 sites.

02

Rollout: what you will see, and when

Each step ends with something visible on docs.ceph.com. Dates are proposals, to confirm with the team.

Sep to Oct 2026

The new front door

Change the front of the site. Move nothing.

  • Rewrite the landing page: seven clear ways in, instead of a feature list.
  • Add seven door pages that point at the existing pages where they already sit. No files move.
  • Group each service's pages under the same five headings.
  • Add one troubleshooting page linking the seven that exist today.
  • One build change switches on the index and the plain-text copies.
  • Agree the page template with the team, and walk the map through with Ville first.
You will see: docs.ceph.com opens on seven clear ways in, and every existing link still works.
Nov to Dec 2026

First service rebuilt

Rebuild one section completely, as the model for the rest.

  • Block (RBD, 41 pages): the smallest and calmest section, and it has no troubleshooting page today.
  • Nine long pages become about thirty, one task each, on the template.
  • Write the troubleshooting pages that are missing.
  • Everything else moves across with metadata added. iSCSI collapses into one retirement page pointing at NVMe-oF.
  • Repeated procedures written once, and redirects for anything that splits.
You will see: one complete section in the new form, beside the old, and a checklist others can follow.
Q1 2027

The rest of the services and Operate

Repeat for the other user-facing sections.

  • CephFS first: its pages are already grouped this way.
  • Then RGW, which leads on reference generated from the code.
  • Cluster operations and deployment, where the duplicated install and upgrade steps finally merge.
  • The OSD management guide: the material exists today, scattered across the docs.
You will see: the user-facing tree fully in the new shape.
Q2 2027

Finish and lock it in

Finish, retire the old navigation, add checks so it stays this way.

  • Developer docs into one track, and the operator pages hiding there move out.
  • Old navigation retired on main. Release branches keep theirs until end of life.
  • Checks in the build for metadata, anchors and template shape.
  • Options and commands published as data, from the same source the pages use.
You will see: a rebuilt docs.ceph.com, and checks that keep it that way.
In the background throughout: the open register items close as each section is rebuilt, so the cleanup never stops but never again sets the agenda.
03

What I need from the team

Approve the direction

The seven doors and the three page types. The companion map places all 618 pages and lists the twenty or so calls that need the team's view.

Pick the first service

Block is my proposal, CephFS next. cephadm instead, if deployment matters more to you.

One subject-matter reviewer per section

For the roughly 90 pages that get rewritten. The docs team reviews the rest, batched per section so nobody gets a trickle.

A comment period on the template

Then it is frozen until the first section ships.

Keep the developer path easy

Developers write most new content and keep writing where they do today. The docs team handles placement. The template is a checklist, not a gate, until the first sections prove it.

The cleanup showed me how the docs break. The rebuild is how they stop breaking.
