# Ceph docs rebuild

*A proposal to the Ceph documentation team. Emmanuel Ameh, September 2026. Draft for review.*

Rendered version: https://eameh-lf.github.io/ceph-docs-rebuild/
Companion: the page-by-page [door map](door-map/).

## In short

Since April I have been on cleanup: 65 defects found, 32 fixed or in review, the rest still in hand. Necessary work, but it fixes pages one at a time and never gets ahead of the problem. The structure itself has to change: stop treating the docs as pages to fix, and rebuild them around what the reader is trying to do. Three moves.

## 1. A new architecture: seven doors, one shape

The top level becomes seven doors, ordered by what the reader is doing. Inside every storage service the same five parts appear in the same order, so once you have learned one section you can find your way around the rest. Nothing is deleted: all 618 pages already have a home, listed page by page in the [companion map](door-map/), and pages only move once the new navigation works.

Parts of the tree already do this. CephFS groups its pages this way but hides the headings, and RADOS is already split by task. This finishes the job and makes it visible everywhere.

Today, 26 sidebar entries on `main`, by component: start, install, cephadm, rados, cephfs, rbd, radosgw, csi, mgr, mgr/dashboard, monitoring, api, architecture, Developer Guide, dev/internals, governance, Technical Charter, foundation, ceph-volume, crimson, releases/general, releases, security, hardware-monitoring, Glossary, Tracing.

Proposed, seven doors, by what the reader is doing:

| Door | Pages today | What it holds |
|---|---:|---|
| 1. Start here | 13 | What Ceph is, choosing a deployment and a release, quick starts |
| 2. Deploy | 21 | cephadm first, Rook and Kubernetes, requirements, and upgrades in one place instead of five |
| 3. Operate | 72 | Running a cluster: pools, CRUSH, monitoring, dashboard, security, maintenance |
| 4. Storage services | 191 | Block, File, Object and Kubernetes, each in the same shape |
| 5. Troubleshoot | 11 | One hub organised by symptom, over the seven pages that exist today plus the ones that are missing |
| 6. Reference | 141 | Options, commands, man pages, APIs, release notes. 37 percent is generated from the code today; the rest follows |
| 7. Develop and contribute | 169 | Developer guide, internals, governance |

The shape inside every service: **Learn, Set up, Operate, Troubleshoot, Reference.**

Page counts are today's pages mapped to each door. About 90 need rewriting; the other 528 need a new home and some metadata. Kubernetes and Django are organised this way, and Canonical and Cloudflare have adopted the same model.

## 2. Modular pages: three types, one template

Every page becomes one of three types and follows one template. A procedure covers one task, says which releases it applies to, and ends with how to check it worked. Repeated procedures are written once and pulled in wherever they are needed, so they cannot drift apart. Creating a pool for RBD images is written out six times in the Block section today, and only one of those copies tells you how to verify it.

- **Concept.** Explains one idea the reader needs before acting. No commands, no steps.
- **Procedure.** One task, numbered steps, one command per step, expected output, verification.
- **Reference.** Facts to look up, not remember: options, commands, limits. Generated from source where possible.

A procedure page, using "Create an erasure-coded pool" as the example:

| Part | Content |
|---|---|
| Metadata | type: procedure. applies to: Squid, Tentacle. reviewed: 2026-09. owner: rados |
| Before you start | Cluster health, permissions, an EC profile chosen |
| Steps | Numbered. One command each, with the output you should see |
| Verify | The command that proves it worked |
| If it fails | The two or three most common failures and what they mean |
| Related | The concept behind it, the reference for every option |
| House rules | Cross-link related pages generously. Example values fail safely if pasted (osd.1701, not osd.0) |

Command reference stays in the man pages, so it still works offline. Prose pages pull the entry from there when the docs are built, rather than repeating it. The first trial is already up as [PR 71609](https://github.com/ceph/ceph/pull/71609).

Red Hat and IBM already write their Ceph guides this way, with the same prerequisites, procedure and verification shape.

## 3. Machine-readable, as a byproduct

This is not a workstream and needs no budget. It falls out of moves 1 and 2: one build change, plus the metadata the template already adds. More people now ask an AI assistant about Ceph, and those assistants read docs.ceph.com. Today they get HTML with no index, and nothing on the page says which release it applies to. The source stays reStructuredText; these outputs are generated by the build, exactly as the HTML is.

| What AI assistants need | Today | After the rebuild |
|---|---|---|
| An index of the docs | Missing: the standard index file, `llms.txt`, is not there | Generated by the build and served at the site root |
| A plain-text copy of each page | Hidden: one exists, but nothing links to it | A Markdown copy of every page, linked and listed in the index |
| Which release a page applies to | Nothing: no page carries that, or a review date, or an owner | Release, review date and owner on every page |
| Options and commands as data | Unpublished: the build already reads them, but only to make HTML | Published as data beside the pages |

Two smaller things follow: stable anchors, so a page or a single procedure can be cited, and as a stretch a service that lets an assistant query the docs directly. `llms.txt` is already served by Anthropic, Cloudflare, GitHub, AWS and 87 of the top 1,000 sites.

## 4. Rollout: what you will see, and when

Each step ends with something visible on docs.ceph.com. Dates are proposals, to confirm with the team.

### Step 1, Sep to Oct 2026: the new front door

Change the front of the site. Move nothing.

- Rewrite the landing page: seven clear ways in, instead of a feature list.
- Add seven door pages that point at the existing pages where they already sit. No files move.
- Group each service's pages under the same five headings.
- Add one troubleshooting page linking the seven that exist today.
- One build change switches on the index and the plain-text copies.
- Agree the page template with the team, and walk the map through with Ville first.

**You will see:** docs.ceph.com opens on seven clear ways in, and every existing link still works.

### Step 2, Nov to Dec 2026: first service rebuilt

Rebuild one section completely, as the model for the rest.

- Block (RBD, 41 pages): the smallest and calmest section, and it has no troubleshooting page today.
- Nine long pages become about thirty, one task each, on the template.
- Write the troubleshooting pages that are missing.
- Everything else moves across with metadata added. iSCSI collapses into one retirement page pointing at NVMe-oF.
- Repeated procedures written once, and redirects for anything that splits.

**You will see:** one complete section in the new form, beside the old, and a checklist others can follow.

### Step 3, Q1 2027: the rest of the services and Operate

Repeat for the other user-facing sections.

- CephFS first: its pages are already grouped this way.
- Then RGW, which leads on reference generated from the code.
- Cluster operations and deployment, where the duplicated install and upgrade steps finally merge.
- The OSD management guide: the material exists today, scattered across the docs.

**You will see:** the user-facing tree fully in the new shape.

### Step 4, Q2 2027: finish and lock it in

Finish, retire the old navigation, add checks so it stays this way.

- Developer docs into one track, and the operator pages hiding there move out.
- Old navigation retired on main. Release branches keep theirs until end of life.
- Checks in the build for metadata, anchors and template shape.
- Options and commands published as data, from the same source the pages use.

**You will see:** a rebuilt docs.ceph.com, and checks that keep it that way.

In the background throughout: the open register items close as each section is rebuilt, so the cleanup never stops but never again sets the agenda.

## 5. What I need from the team

1. **Approve the direction.** The seven doors and the three page types. The [companion map](door-map/) places all 618 pages and lists the twenty or so calls that need the team's view.
2. **Pick the first service.** Block is my proposal, CephFS next. cephadm instead, if deployment matters more to you.
3. **One subject-matter reviewer per section.** For the roughly 90 pages that get rewritten. The docs team reviews the rest, batched per section so nobody gets a trickle.
4. **A comment period on the template.** Then it is frozen until the first section ships.
5. **Keep the developer path easy.** Developers write most new content and keep writing where they do today. The docs team handles placement. The template is a checklist, not a gate, until the first sections prove it.

*The cleanup showed me how the docs break. The rebuild is how they stop breaking.*
